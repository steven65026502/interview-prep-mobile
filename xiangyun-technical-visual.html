所有技術題都用同一副骨架

真正要背的只有四個動作。即使遇到沒看過的題目，也能先把思路講完整。

1. 定義一句話說它是什麼，不先堆名詞。
2. 理由它解決什麼問題，為什麼這樣選。
3. 證據用自己的 Demo 或論文舉一個例子。
4. 限制說驗證方式與尚未處理的邊界。
記憶句：先說人話，再畫資料流；先承認條件，再給可驗證的方法。
01

RAG 與 Fine-tuning 差在哪裡？

把它想成「考試可以翻資料」與「重新訓練答題習慣」，兩者改動的位置不同。

30 秒口語回答

定義RAG 是回答前先取得外部文件，再把文件交給模型；Fine-tuning 則是用範例資料調整模型參數與行為。

理由需要最新資料、來源引用或權限控管時，我會先選 RAG；需要固定格式、語氣或任務習慣時，才評估微調。

限制Fine-tuning 不等於可靠記住最新事實，所以企業文件問答通常先把資料、檢索與評測做好。

不要說：「Fine-tuning 就是把公司的所有知識灌進模型。」
02

為什麼 BM25＋BGE＋RRF？

兩個檢索器像兩位擅長不同線索的調查員，RRF 不比較兩人的原始分數，而比較各自排出的名次。

40 秒口語回答

定義BM25 對關鍵詞、代碼與條文很敏感；BGE 可以找出用詞不同但語意相近的內容。

理由兩者原始分數不在同一尺度，所以我用 RRF 依名次融合，而不是硬把分數相加。

證據我的 MedEvidence 公開版就是這條流程，會顯示兩路召回、融合排名與 Top 3 來源。

限制混合不一定永遠較好，仍要用固定題庫比較 Top-k 命中與引用支持度。

不要只說：「混合檢索比較準。」要補上兩路各自補什麼，以及怎麼驗證。
03

怎麼降低幻覺？

不是加一句「請不要亂講」。要把防線分散在資料、檢索、回答、動作與評測五層。

40 秒口語回答

主張我不會只靠 Prompt 降低幻覺，而會做多層控制。

先管理資料來源與版本，檢索時加上權限和門檻；回答只能根據通過門檻的證據並附來源。資料不足時拒答，高風險操作交由人工確認。

驗證最後保存問題、檢索結果、模型版本與回答，用固定題庫檢查正確性、引用支持度、拒答與延遲。

有引用不代表答案正確；仍需確認引用內容真的支持那一句結論。
04

Workflow 與 Agent 怎麼選？

先問路徑是否需要動態決策。固定路徑用 Workflow，真正需要臨場選工具才讓 Agent 決定。

35 秒口語回答

定義Workflow 的步驟與分支由程式預先定義；Agent 則會依目標和當下狀態選擇工具與下一步。

取捨能用固定流程解決時，我會先採 Workflow，因為較容易測試、控管權限與預估成本。只有路徑確實需要動態決策時才加入 Agent。

安全Agent 仍需工具 allowlist、步數上限、timeout、稽核紀錄與高風險動作人工核准。

05

API 很慢，你怎麼找原因？

先量每一段，不先猜。平均值也不夠，要看 p50、p95、錯誤率與流量條件。

40 秒口語回答

第一步先確認流量與服務目標，量測 p50、p95、錯誤率及各階段耗時，而不是先猜資料庫慢。

第二步定位瓶頸後，再選擇索引、連線池、快取、batch、非同步 I/O 或縮短 context。

驗證修改後用相同資料與負載重測，同時檢查答案品質與錯誤率，避免只是把速度換成錯誤。

不要一聽到慢就回答「加 Redis」；先說怎麼證明瓶頸值得快取。
06

現場突然出一題系統架構，怎麼開口？

不要立刻畫框架名稱。先把假設問清楚，接著依五階段把答案搭起來。

萬用開場句

「在開始畫架構前，我想先確認使用者規模、文件量與更新頻率、可接受延遲、資料權限，以及這個回答出錯時的風險。若先假設是企業內部文件問答、需要引用且文件有權限，我會這樣設計……」

接著照圖上的五層往下講。遇到不熟的元件，可以說「這裡需要依流量與團隊既有技術棧再選型」，不要硬猜。

07

「你是不是都靠 AI 做？」怎麼回答？

不要防衛，也不要把 AI 隱藏掉。把工作切成「AI 加速」與「你負責成果成立」兩張責任清單。

45 秒口語回答

我確實會使用 Claude Code、Codex 等工具協助理解程式、比較方案與產生初版，但我會先定義需求和限制，檢查 Git diff，親自執行測試並核對輸出。

以 RAG Demo 為例，是否採 BM25、BGE、RRF，如何處理降級、拒答與固定評測，都必須由我理解後才能決定。AI 加速實作，但系統為什麼這樣設計、結果是否成立及限制如何說明，由我負責。

不要說：「程式都是 AI 寫的，我主要負責下 Prompt。」也不要反過來假裝完全沒用 AI。
08

你的 Demo 到底是不是完整 RAG？

這題要主動說清楚部署邊界。公開版展示可重現檢索與治理，本機版才包含 FastAPI 與 Ollama。

被追問時這樣回答

典型 RAG 會包含檢索與生成。我的公開版受靜態託管限制，主要展示混合檢索、來源引用、拒答與稽核，回答採可重現的證據式整理；本機 FastAPI 版才會把後端重新驗證的 Top 3 文件交給 Ollama。

所以我會稱它為 RAG 治理與檢索原型，而不是已完成的商用醫療生成系統。正式上線還需要身分權限、受控模型服務、監控、資安與更完整評測。
