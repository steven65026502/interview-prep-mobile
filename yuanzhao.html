我的碩士研究處理的是 S-111 海流與 S-104 水位這類動態海洋資料。原本不同日期、時間、預報時距與位置的品質結果不容易保存和回查，因此我建立一套從資料轉換、時空配對、誤差計算到資料庫、API 與 QGIS 展示的流程。

我主要負責 Python 資料處理、PostgreSQL 資料設計、Flask 唯讀 API、QGIS 圖層呈現，以及數值與資料完整性驗證。最後完成 42 個目標日、114 組日期與預報時距的一致性檢查，並用 11 個氣象署浮標站做有限外部比對。

這個研究和機器人工作的連結，是我已經有把多種資料來源、後端服務與檢視端串成完整流程的經驗，也知道如何用紀錄、測試和外部資料確認系統不是只有表面上能跑。

被追問「你本人到底做了什麼」

我負責把研究需求轉成資料流程，包括來源資料解析、時間與空間配對、誤差計算、資料庫欄位、API 查詢和 QGIS 圖層呈現，也反覆核對輸出數值與原始資料。遇到格式、單位或基準不一致時，我會先找來源定義，再用小樣本實算與全資料檢查確認。

被追問「最難的問題是什麼」

最難的不是單一公式，而是確保不同檔案代表同一有效時間、同一位置與同一物理意義。我的做法是先建立明確索引與資料字典，再用已知樣本逐筆重算，最後做完整資料集的一致性檢查。這讓我學會先確認資料語意，再處理程式結果。

被問到「論文是不是靠 AI 做的」

我有使用 AI 協助查找方向、整理程式與檢查文字，但研究問題、資料來源、方法選擇、數值核對與最後判讀由我負責。AI 產出的內容不會直接當成結論，我會回到原始資料、官方規格、程式測試與實際輸出驗證。我也能說明每一個模組的輸入、輸出、限制和曾經修正的問題。

Technical essentials

今晚技術補強重點

目標是能說清楚基本概念與除錯流程，不是假裝已有產品實戰經驗。

DDS 是什麼
  • Data Distribution Service，是即時系統常用的資料中心式發布／訂閱通訊標準。
  • 發布者送出資料，訂閱者依主題接收，不必彼此緊密綁定。
  • QoS 可控制可靠度、期限、歷史資料、持久性等傳輸行為。
  • 適合多設備、多節點、低延遲且需要可靠交換狀態資料的系統。

安全答法：我目前理解概念與使用情境，尚未在實際設備上部署 RTI Connext DDS。

ROS 2 與 DDS 的關係
  • ROS 2 以 node 組成系統，常透過 topic 傳送持續資料，service 處理短請求，action 處理較長任務。
  • ROS 2 的底層通訊通常使用 DDS 實作，但 ROS 2 提供更貼近機器人開發的抽象。
  • 面試不需要假裝熟練，只要能說明你會從 topic、訊息格式、QoS、log 與節點連線開始查問題。
DDS 和 REST API 有何不同
REST常見為請求／回應，適合查詢、管理與一般 Web 服務。
DDS發布／訂閱、即時資料流、多節點自動探索與細緻 QoS。
你的連結你已有 REST 與資料庫經驗，可說明會把即時設備資料層與查詢服務層分開理解。
現場設備故障時的處理順序
  1. 先確認人員安全、設備風險、影響範圍與是否需要停止操作。
  2. 取得時間、環境、操作步驟、錯誤訊息與是否可穩定重現。
  3. 檢查電源、線材、網路、IP、連線狀態與必要的服務程序。
  4. 查看裝置、應用程式與後端 log，區分硬體、網路、驅動或軟體層。
  5. 建立最小測試，替換單一元件或關閉非必要模組，逐層隔離問題。
  6. 提出可回復的暫時方案，完整記錄修改，必要時升級給原廠或資深工程師。
  7. 結案後補上根因、處置與預防方式，讓同一問題可以被快速回查。
可能被確認的基礎能力
  • Python：JSON、API、例外處理、logging、資料處理。
  • C/C++：如實說明目前程度，不把課程經驗說成產品開發經驗。
  • Linux：檔案、程序、網路、權限與 log 的基本查找方式。
  • 網路：IP、port、TCP/UDP、ping、連線測試與防火牆概念。
  • Git：版本、分支、commit、diff 與回溯修改。
  • Docker：容器、映像檔、port、volume 與 log 的基本概念。
