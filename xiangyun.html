90 秒 RAG 專案講法
我做的 MedEvidence 是公開文件問答與治理稽核原型。使用者可以自由輸入問題，系統先做範圍與風險判定，再以 BM25 召回關鍵詞相近文件、用 BGE 中文向量補足語意相近但字面不同的文件，最後以 Weighted RRF 合併排名。公開版為了可重現與避免假裝接了雲端模型，採決定式 evidence-extractive 整理；本機 FastAPI 版才把後端重新驗證過的 Top 3 文件交給 Ollama。系統另外保存來源、延遲與 request id，並用固定題庫做回歸測試。這個專案讓我實際處理了檢索品質、失敗降級、引用可信度與 AI 回答不能只看起來合理的問題。
60 秒碩士論文講法
我的碩士研究不是建立預報模型，而是做動態海洋資料的品質監測系統。原始資料有不同格式、日期、預報時距與空間位置，我用 Python 完成解析與配對，將結果寫入 PostgreSQL，由 REST API 提供查詢，再在 QGIS 重建空間圖層。為避免轉換或寫入過程改變結果，我以原始資料重算 114 組，與資料庫全部一致。這段經驗證明我能處理異質資料、資料庫與 API，也會為系統建立可追溯的驗證證據。

Likely questions

高機率問答

你用 AI 工具做很多，哪些是你自己做的？
我會用 AI 協助理解程式、比較方案與產生初版，但我負責把需求與限制說清楚、決定資料語意和驗證方式、檢查 git diff、親自執行測試並核對輸出。以 RAG Demo 為例，是否使用 BM25、BGE、RRF、如何降級、哪些資料可送進模型、怎麼拒答與做固定評測，都必須由我理解後才能決定。AI 加速實作，但成果是否成立由我負責。
RAG 和 fine-tuning 有什麼不同？
RAG 在推論時檢索外部知識，適合需要更新、引用及權限控制的內容；fine-tuning 改變模型行為或輸出風格，並不等於把最新事實可靠存進模型。企業文件問答通常先做好資料、檢索與評測，再判斷是否真的需要微調。
為什麼同時用 BM25、BGE 與 RRF？
BM25 對產品名、條文、代碼等精確字詞強；BGE 能找出字面不同但語意相近的內容。兩者原始分數尺度不同，RRF 直接依排名融合，比硬把分數正規化後相加更穩健也更容易解釋。之後仍要用固定題庫比較 hybrid 是否真的優於單一路徑。
怎麼降低幻覺？
先改善檢索與 metadata 篩選，再限制模型只能根據通過門檻的證據回答；要求逐項引用、資料不足時拒答，並驗證引用是否真的支持句子。對高風險輸出加入人工核准，最後用固定測試集檢查回答正確率、引用正確率、拒答與延遲。
Workflow 和 Agent 有什麼不同？
Workflow 的步驟與分支由程式預先定義，較可控、易測試；Agent 會依目標與當下狀態選擇工具或下一步，彈性高但風險也高。能用明確 workflow 解決的問題，我會先採 workflow；只有路徑確實需要動態決策時才加入 agent loop。
你怎麼理解 AI Harness Engineering？
我理解它不是單一模型或 Prompt，而是模型外層的執行支援：任務規格、context 選擇、工具與權限、狀態與記憶、觀測紀錄、失敗歸因及完成前驗證。我的專案已做過來源限制、工具／資料邊界、降級、audit 與 regression test，但我不會宣稱已建成完整商用 harness；我也想請教貴公司內部對這個詞的具體定義與目前架構。
需求很模糊時，你會怎麼做？
先確認使用者、決策情境、輸入來源、期望輸出、不能做的事與驗收標準，再用一個小案例確認理解一致。先交付最小可驗證流程，保留 log 與失敗案例；若需求改變，能看出影響的是資料、檢索、模型、工具還是介面，而不是直接猜著開發。
客戶說 AI 回答不好，你怎麼查？
先保存問題、版本、檢索候選、最終 context 與回答，再分類是知識缺漏、切塊／metadata、召回、排序、Prompt、模型或使用者期待問題。建立可重現案例後只改一個變因，以固定題庫比較改善前後，並檢查其他題是否退步。
Agent 呼叫會改資料的工具，怎麼避免重複執行？
工具使用明確 schema 與最小權限；寫入動作帶 idempotency key，先檢查狀態再執行，設定 timeout 與有限 retry。付款、刪除、寄信等高風險動作在真正送出前由人確認，並保存 request id、輸入、結果與錯誤，讓整段可追溯。
如果 API 很慢，你會先做什麼？
先定義流量與目標，查看 p50、p95、p99、錯誤率和每個階段耗時，不只看平均值。再依瓶頸考慮索引、連線池、快取、batch、非同步 I/O 或縮短 context；修改後用相同負載重測，確認延遲改善且答案品質沒有下降。
你最大的技術缺口是什麼？
我目前的主要缺口是正式商用環境的大流量部署與跨客戶交付經驗，Linux、Docker 和雲端維運也需要透過實際專案深化。不過我已能完成資料、API、檢索、測試與文件的端到端原型，也習慣明確標示不知道的地方並用可驗證方式補齊。

系統架構題的固定回答順序
1. 先問條件：使用者、資料量、更新頻率、延遲、權限與風險。
2. 畫資料流：輸入 → API → 檢索／模型／工具 → DB → 回應。
3. 補失敗處理：timeout、retry、idempotency、fallback、人工核准。
4. 說可觀測性：request id、log、metrics、trace。
5. 說驗證：固定案例、負載、邊界與回歸測試。
簡化版 RRF 程式題
def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

說明重點：輸入是多組文件排名；同一文件在不同召回器排名越前，融合分數越高。正式版還要處理權重、重複 ID、空結果、Top-k 與測試。

Prompt injection 與資料權限
將外部文件視為不可信資料，不讓文件文字覆蓋 system 指令；工具採 allowlist 與最小權限，敏感資料先做使用者與文件層級授權。前端送來的文件內容不直接信任，後端依文件 ID 重新取得可信版本。高風險工具需人工核准，所有動作保留 trace。
今晚最低練習：手寫一個 JSON 清理函式、一題 SQL 最新紀錄、一段 API timeout／retry；再用白紙畫一次 RAG＋Agent 系統架構。不要臨時狂背框架 API。
